# German Steels CRM Frontend API Migration Guide

**Audience:** frontend developers working in this repository  
**Prepared from:** the current frontend source plus the four backend notes supplied on 9 September 2026  
**Goal:** replace legacy API calls with the current CRM API contracts, page by page, without silently changing business behaviour.

## 1. Source documents and precedence

This guide reconciles:

- `TARGET_SALARY_DISTANCE_ENDPOINTS.md`
- `RETAIL_ATTENDANCE_ENDPOINTS.md`
- `CRM_PROCESS_FLOW_GUIDE.md`
- `REMAINING_ENDPOINTS.md`
- the calls currently present under `app/`, `components/`, and `lib/`

The supplied documents contain a few conflicting names. Until the backend publishes an OpenAPI contract, use this proposed precedence and confirm the conflicts in section 4 before implementing those calls:

1. Use `TARGET_SALARY_DISTANCE_ENDPOINTS.md` for targets, salary breakdowns, and Ola Maps distance.
2. Use `RETAIL_ATTENDANCE_ENDPOINTS.md` for retail, shared visits, attendance, attendance rules, travel rates, and monthly salary.
3. Use `REMAINING_ENDPOINTS.md` for auth/users, access control, master data, employees, teams, empanelment, projects, documents, expenses, tracking, dashboard, and notifications.
4. Use `CRM_PROCESS_FLOW_GUIDE.md` for workflow and stage behaviour, but not to override a more specific endpoint contract.

This precedence is a frontend recommendation, not a confirmed backend versioning rule.

## 2. Global frontend contract

### Base URL and headers

Current backend base URL:

```text
http://ec2-18-211-58-135.compute-1.amazonaws.com:8081
```

All protected requests must include:

```http
Authorization: Bearer <token>
Accept: application/json
Content-Type: application/json
```

Do not hard-code the base URL in pages or components. Move it to one shared configuration value, preferably `NEXT_PUBLIC_API_BASE_URL`, and route all calls through one request helper. Multipart uploads must let the browser set the `Content-Type` boundary.

### Authentication and authorization

- Login with `POST /api/auth/login` and store the returned `token`.
- Load the signed-in profile with `GET /api/auth/me`.
- Let the backend apply data visibility from the token and scopes.
- Do not send creator, author, changed-by, or uploader employee IDs when the endpoint derives them from the token.
- A `403` means the action is outside the user's role/scope. It must not be shown as an empty result.
- On `401`, clear the local session and send the user to login.

### Pagination

Every documented list endpoint is paginated. The frontend should expect a Spring-style page and preserve the backend page index rather than downloading every page:

```ts
interface ApiPage<T> {
  content: T[];
  number: number;       // zero-based page index
  size: number;
  totalElements: number;
  totalPages: number;
  first?: boolean;
  last?: boolean;
  empty?: boolean;
}
```

Some supplied notes do not show the exact response envelope. Before removing compatibility normalizers, capture one real response for every endpoint in the target environment and confirm whether the page is returned directly or under `data`.

### Mutation behaviour

- IDs are generated by the backend. Only relationship IDs belong in create payloads.
- Documented `PUT` calls behave like partial updates: omitted fields remain unchanged.
- Do not assume `null` clears a relationship. Use a dedicated clearing endpoint where documented.
- Documented deletes are normally soft deletes/deactivations; keep history visible where the screen supports it.
- Treat `200`, `201`, and `204` as successful mutation statuses. The supplied notes do not consistently define mutation response bodies.
- Create flows that need the new ID immediately must confirm whether the response is an object, an ID, or an empty body. This is a backend contract gap.

### Standard error handling

The shared request helper should parse, in order:

1. JSON `message`, `error`, or validation fields.
2. Plain response text.
3. HTTP status fallback.

Show backend validation messages for GSTIN, PIN/region mismatch, invalid stage transition, duplicate check-in, and scope failures.
